# Firmware Update Lab

Локальний стенд для перевірки OTA-оновлень детекторів. Сервер написаний на Express і TypeScript, дані зберігаються у SQLite через Prisma, а адмінка — це React-застосунок із Tailwind CSS. Справжнє встановлення прошивки не виконується: усі сценарії моделюються з браузера, а результати зберігаються в загальній історії.

## Вимоги

- Node.js 20+
- npm

## Запуск

```bash
npm install
cp .env.example .env
npx prisma generate
npx prisma migrate dev --name init
npm run db:seed
npm run build
npm run dev
```

Відкрийте http://localhost:3000. Стандартний токен адміністратора: `local-admin-token-change-me` — він призначений лише для локального стенда.

`npm run build` збирає React/Tailwind інтерфейс у `public/`, який віддає Express. Після зміни файлів у `frontend/` виконайте збірку повторно.

## Робота з адмінкою

### 1. Додайте пристрій

У блоці **«Додати пристрій»** заповніть:

- **ID пристрою** — унікальний ідентифікатор, наприклад `detector-002`;
- **секретний ключ** — ключ, який пристрій передає під час автентифікації;
- **модель** — наприклад `D-100`;
- **ревізію заліза** — наприклад `rev-A`.

Модель і ревізія зберігаються разом із пристроєм. Саме ця пара визначає, чи може пристрій отримати конкретну прошивку. Ключ зберігається на сервері як SHA-256-хеш.

### 2. Завантажте прошивку

У блоці **«Завантажити прошивку»** виберіть тестовий файл і вкажіть його версію, модель, ревізію та опис змін. Файл зберігається локально, а сервер записує його розмір і SHA-256. Для реального device API версія повинна бути новішою за поточну на пристрої, а модель і ревізія мають збігатися точно.

### 3. Запустіть тест

У блоці **«Запустити тест оновлення»** виберіть у випадаючих списках пристрій, прошивку і потрібний сценарій, а потім натисніть **«Запустити сценарій»**. Інтерфейс одразу показує, чи збігаються модель і ревізія. Результат виконання відображається в повідомленні та потрапляє до таблиць історії. Обраний тестовий сценарій примусовий: наприклад, `CORRUPT_FILE` буде відтворено навіть якщо ця версія вже встановлена після попереднього тесту.

Для перевірки доступних версій виберіть **«Перевірити нову версію»**: список прошивок покаже лише файли, сумісні з моделлю та ревізією вибраного пристрою. Результат показує поточну версію пристрою та найновішу сумісну версію зі сховища, незалежно від вибраного пункту списку. Щоб змоделювати старішу або новішу поточну версію, виберіть **«Задати поточну версію»**, введіть значення (наприклад, `1.0.0`) і після цього запустіть перевірку оновлень.

## Сценарії тестування та статуси

| Сценарій | Що перевіряє | Підсумковий статус | Результат |
|---|---|---|---|
| Успішне оновлення | Сумісність моделі та ревізії | `SUCCESS` | Створюється сесія оновлення, а поточна версія пристрою змінюється на версію прошивки. |
| Оновлення немає | Явно обраний сценарій | `NO_UPDATE` | Сесія оновлення не створюється. |
| Неправильний ключ | Відмову в автентифікації | `AUTH_FAILED` | До історії помилок додається запис про відхилений ключ. |
| Немає діагностики | Заборону оновлення без діагностичних даних | `DIAGNOSTICS_REQUIRED` | Оновлення не пропонується і сесія не створюється. |
| Втрачено зв’язок | Переривання після надсилання діагностики | `DISCONNECTED` | Перевірка сумісності та сесія оновлення не створюються, тому сценарій працює для будь-якої вибраної прошивки. |
| Пошкоджений файл | Перевірку цілісності SHA-256 | `INTEGRITY_ERROR` | Сесія завершується помилкою, а історія помилок містить запис про контрольну суму. |
| Помилка встановлення | Помилку пристрою на етапі застосування | `INSTALL_ERROR` | Сесія завершується помилкою встановлення, поточна версія пристрою не змінюється. |
| Попередження пристрою | Збереження діагностичної помилки разом з оновленням | `SUCCESS` і `E_SENSOR_WARN` | Попередження датчика зберігається в історії, а оновлення завершується успішно. |
| Перевірити нову версію | Пошук останньої сумісної версії | `UPDATE_AVAILABLE` або `NO_UPDATE` | Показує поточну версію та, за наявності, найновішу сумісну прошивку; сесія оновлення не створюється. |
| Задати поточну версію | Ручну зміну версії пристрою для тесту | `FIRMWARE_VERSION_SET` | Зберігає введену версію як поточну, щоб перевірити доступність оновлення від потрібної точки. |

Якщо вибрані модель або ревізія не відповідають прошивці, сервер повертає `INCOMPATIBLE_FIRMWARE`. У такому разі сесія оновлення не створюється, а версія пристрою не змінюється.

У таблиці **«Історія оновлень»** зберігаються запропоновані та завершені оновлення. У таблиці **«Історія помилок»** — помилки автентифікації, цілісності, встановлення й діагностики. Статуси `OFFERED`, `CONFIRMED` і `DOWNLOADING` позначають проміжні етапи, `SUCCESS` — завершення без помилок, а `*_ERROR`, `AUTH_FAILED` і `DISCONNECTED` — проблемні сценарії.

## API для пристрою

Усі запити пристрою, крім початкового `hello`, автентифікуються заголовками:

- `X-Device-ID: detector-001`
- `X-Device-Key: test-device-key`

### 1. Перше звернення
`POST /api/device/hello`

```json
{"deviceId":"detector-001","key":"test-device-key"}
```

### 2. Діагностика
`POST /api/device/diagnostics`

```json
{
  "model":"D-100",
  "hardwareRev":"rev-A",
  "firmwareVersion":"1.0.0",
  "status":"OK",
  "batteryPercent":84,
  "uptimeSeconds":86300,
  "errors":[],
  "extra":{"temperatureC":27.4,"signalDbm":-63}
}
```

`extra` — розширюваний JSON-об'єкт для майбутньої діагностики. `errors` — масив `{ "code": "E_SENSOR", "message": "...", "details": {} }`.

### 3. Перевірка оновлення
`GET /api/device/update-check`

Якщо діагностики ще не було — сервер повертає `409 DIAGNOSTICS_REQUIRED`. Якщо є сумісніша новіша версія, повертає `updateId`, версію, changelog, розмір і SHA-256. Сумісність визначається точно за парою `model + hardwareRev`.

### 4. Підтвердження, завантаження, результат
- `POST /api/device/updates/:id/confirm`
- `GET /api/device/updates/:id/download`
- `POST /api/device/updates/:id/result` з одним із `SUCCESS`, `INTEGRITY_ERROR`, `INSTALL_ERROR`, `DOWNLOAD_ERROR`.

При успіху передайте `{"result":"SUCCESS","firmwareVersion":"1.1.0"}`. Для помилок додайте `message`.

## Адмін API
Усі запити потребують заголовок `X-Admin-Token`:
- `GET /api/admin/devices`
- `GET /api/admin/firmware`
- `GET /api/admin/events`
- `POST /api/admin/devices` JSON `{ "id":"detector-002", "key":"some-secret", "model":"D-100", "hardwareRev":"rev-A" }`
- `POST /api/admin/firmware` multipart: `file`, `version`, `model`, `hardwareRev`, `changelog`
- `POST /api/admin/test-runs` JSON `{ "deviceId":"detector-002", "firmwareId":"...", "scenario":"SUCCESS" }`

## Важливі межі прототипу
- Це демонстраційна основа, не production OTA-сервер. Не виставляйте її в інтернет без посилення захисту.
- Ключ пристрою зберігається у вигляді SHA-256-хешу, але початковий `hello` передає ключ у тілі запиту — використовуйте тільки локально або через HTTPS у реальному середовищі.
- Поки немає ротації ключів, обмеження частоти запитів, ролей адмінів, підпису прошивки, атомарної системи rollout/rollback чи перевірки цифрового підпису. SHA-256 перевіряє цілісність файлу, але сам по собі не доводить, що прошивка довірена.
- «Пропав зв'язок» у прототипі визначається через `lastSeenAt`; окремий фоновий heartbeat/online state можна додати наступним кроком.
- Версії порівнюються простим numeric dotted-version comparator (наприклад `1.10.0 > 1.2.0`). Для складних SemVer prerelease-версій варто перейти на пакет `semver`.
